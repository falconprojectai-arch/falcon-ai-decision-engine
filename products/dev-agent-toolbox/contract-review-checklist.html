7 checks before trusting a JSON API or AI-agent response

A response can be valid JSON and still break your integration. Use this short checklist to catch common contract mismatches before shipping. It is a practical preflight, not a substitute for full production tests.

1. Required fields

Check that every required field exists in successful, error, and partial-response cases. Do not assume a field will always be present just because it appeared in one example.

2. Field types

Test strings versus numbers, booleans versus string values such as "true", arrays versus objects, and integer versus decimal values where the consumer expects a specific type.

3. Null, missing, and empty are different

Decide whether null, a missing key, "", [], and {} are all acceptable. Clients often handle these states differently.

4. Enum and status values

Enumerate allowed states and test unknown or newly added values. A downstream switch statement may fail when an API adds a status the client does not recognize.

5. Extra fields and sensitive data

Decide whether additional properties are permitted. Check that debug traces, internal prompts, access tokens, and personal data do not leak into public responses.

6. Boundary and failure cases

Include empty arrays, long strings, zero values, missing nested objects, malformed JSON, timeouts, rate-limit responses, and errors that use a different schema from success responses.

7. Schema drift over time

Keep representative payloads from real versions and rerun them when the provider, model, prompt, tool definition, or API version changes. A successful HTTP status alone does not prove the response matches your contract.
