Integrating blockchain infrastructure into an AI agent

This guide shows two practical patterns: passing an affiliate reference when an agent creates a domain order, and connecting an agent to blockchain RPC tools. The examples use public documentation and placeholders for credentials. They do not make purchases or sign transactions.

Last reviewed: 12 November 2026. Provider features and terms can change; verify the linked official docs before deployment.

1. StableDomains: attach a referral code to an order

StableDomains documents a ref field on order, cart and transfer requests, and the X-SD-Ref header for REST. This lets a tool builder preserve referral attribution when a user explicitly asks an agent to register a domain. The user still controls the purchase and payment step.

Example REST request (replace the example domain and API key only in your own environment):

curl -X POST https://stabledomains.net/api/v1/orders \
  -H "Authorization: Bearer $STABLEDOMAINS_API_KEY" \
  -H "Content-Type: application/json" \
  -H "X-SD-Ref: ff6ueixx" \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{"domain":"your-project-name.com","years":1,"dry_run":true}'

This is a dry run: it checks availability and pricing without creating an order or charging the user. Only remove dry_run after the user reviews the final quote and explicitly approves proceeding.

Equivalent MCP tool call:

{
  "name": "create_order",
  "arguments": {
    "domain": "your-project-name.com",
    "years": 1,
    "dry_run": true,
    "ref": "ff6ueixx"
  }
}

Important safeguards:

  • Do not create an order unless the user explicitly requested that domain purchase.
  • Show the final domain, term, renewal price and payment requirements before asking for approval.
  • Do not store API keys in prompts, public repositories or browser code.
  • Never ask a user for a seed phrase or private key.
  • Do not pay or sign on behalf of a user without explicit transaction approval.

2. SwiftNodes: connect an agent to RPC tools

SwiftNodes documents a hosted MCP endpoint for compatible agent clients. Public tools can be used without a key; authenticated RPC usage requires an API key. Keep that key in a secret manager or environment variable.

Example MCP configuration (use your own secret environment variable; do not commit a real key):

{
  "mcpServers": {
    "swiftnodes": {
      "url": "https://rpc.swiftnodes.io/mcp",
      "headers": {
        "Authorization": "Bearer ${SWIFTNODES_API_KEY}"
      }
    }
  }
}

Example read-only JSON-RPC request for Base:

curl -X POST "https://rpc.swiftnodes.io/rpc/base?key=$SWIFTNODES_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","method":"eth_blockNumber","params":[],"id":1}'

Before production, check supported methods and chain availability, measure latency and errors from your deployment region, review the active plan's request limits, rotate credentials and configure a fallback. A working endpoint is not a guarantee of uptime or suitability for every workload.

Start with public MCP discovery

SwiftNodes' hosted MCP server exposes several discovery and diagnostic tools without an API key: list_chains, get_chain, get_pricing, get_method_support, and probe_endpoint. The documented rpc_call and get_account tools require an API key. This lets a builder inspect chain coverage, endpoint templates, method support and plan information before adding credentials. SwiftNodes also says its server is listed in the official MCP Registry as io.swiftnodes/swiftnodes.

Rate-limit caveat: official pages currently disagree

The official Getting Started page says the Free plan includes 2 HTTP requests per second. The dedicated Rate Limits page lists 20 requests per second for Free and separately says the shared demo key is limited to 2 requests per second; the homepage also advertises 20. Until the provider clarifies whether the Getting Started text is outdated, design conservatively around 2 requests per second for a new Free key, implement backoff for HTTP 429, and verify the limit shown in your own dashboard.

3. A safe agent workflow

  1. Discover options and retrieve current prices using read-only calls.
  2. Present alternatives, renewal costs, supported network and provider limits to the user.
  3. Ask for explicit approval before creating a paid order or using a balance.
  4. Use idempotency keys and bounded retries for order creation.
  5. Return the provider's order ID and payment instructions; never claim success before the provider confirms it.
  6. Keep referral metadata transparent and secondary to the user's choice.
